# 鼓譜卡拉OK — 架構與執行計畫

> 狀態：討論稿 v0.2（2026-11-17）。已用一份真實樣本譜（Dance Monkey）驗證過，見第 12 節。尚未寫正式程式；現有 artifact 只是概念原型。

## 1. 一句話目標

小孩打鼓時，iPad 上的譜**跟著 YouTube 上的歌一起走**，隨時知道「現在第幾小節、下一個要打什麼、什麼時候進場」。

## 2. 已確認的事實（來自討論）

| 項目 | 結論 |
|---|---|
| 使用者 | 小孩打鼓，iPad 放譜架（橫放、大螢幕） |
| 最大痛點 | **譜跟歌對不起來**（不知道歌現在走到譜的哪裡） |
| 音樂來源 | App 內嵌 YouTube 播放，譜跟著影片時間走 |
| 譜的來源 | 老師給的五線譜 PDF，僅個人使用 |
| 譜與歌的關係 | 簡化版／老師改編；小節結構與原曲一致 |
| 歌的速度 | 大多是流行歌，速度固定 |
| 音符複雜度 | 八分、十六分音符（現階段） |
| 輸入方式 | PDF 丟給 Claude 轉成譜資料，貼進 App；App 內可微調 |

**樣本譜補充的事實**（討論時沒提到，但樣本裡有）：多小節休止、反覆記號（含 4x、3x）、段落標題、譜上有小節號。這些都會影響 v1 的範圍，見第 12 節。

## 3. 核心洞察

這個 App 的價值不在「捲動動畫」（原型已做出來），而在**把譜的位置對應到 YouTube 的時間（秒）**。

兩條原則：

1. **所有畫面只認「拍位置（beat）」，不認秒數。** 秒數到拍位置的換算集中在「時間對照層」，以後換算法，其他部分不用改。
2. **有兩套小節號：「譜上小節號」和「播放順序」。** 小孩看的是紙上的小節號，但有反覆記號時，實際播放的小節數比譜上多。畫面顯示譜上小節號，內部用播放順序算時間。

## 4. 對齊策略（由簡到難）

| 級別 | 做法 | 適用 | 時機 |
|---|---|---|---|
| A. BPM + 第1拍位置 | 拍位置 = (影片秒數 − 第1拍秒數) × BPM / 60 | 速度固定的錄音室流行歌 | **v1 做這個** |
| B. 錨點（anchors） | 在幾個小節標記「第N小節 = 第X秒」，中間線性內插 | 輕微漂移、變速、現場版 | v2，需要時再加 |
| C. 自動節拍偵測 | 分析音訊自動找拍子 | — | 不做（YouTube 音訊拿不到） |

另外，錨點也是修正「反覆次數猜錯」的保險：不管譜怎麼展開，只要某幾個小節對得上影片，其他就能跟著對。

**v1 的對拍用「兩點校準」，不直接信譜上的 ♩=。** 譜上的速度和影片實際速度常差 1% 左右，累積到歌尾會差到一小節（樣本實例見第 12 節）。做法：標記「第一個進場小節」和「接近結尾的某個小節」各一次，App 由這兩個點算出 BPM 與第1拍位置。

## 5. 模組切分

```
┌─────────────────────────────────────────────┐
│ UI：曲庫 / 播放頁 / 編輯頁 / 對拍工具          │
├─────────────────────────────────────────────┤
│ 練習控制：速度、A-B循環、節拍器、跳到小節       │
├─────────────────────────────────────────────┤
│ 譜面渲染（canvas，只吃「拍位置」）             │
│   軌道、判定線、小節線、休止倒數、下一擊提示    │
├─────────────────────────────────────────────┤
│ 時間對照層 TimeMap：秒 ⇄ 拍                   │
│   v1 = 線性(BPM, 第1拍)；v2 = 錨點分段線性     │
├─────────────────────────────────────────────┤
│ 時鐘層 Clock：提供「現在的影片秒數」           │
│   YouTubeClock（輪詢 + 本地插值）              │
│   InternalClock（沒影片時，純節拍器練習）       │
├─────────────────────────────────────────────┤
│ 譜展開層 Expander（v1 必備）                   │
│   多小節休止 → 逐小節；反覆記號 → 播放順序      │
│   保留每個播放小節對應的「譜上小節號」          │
├─────────────────────────────────────────────┤
│ 譜資料層：JSON ⇄ 記憶體；曲庫儲存；匯入/匯出   │
└─────────────────────────────────────────────┘
```

各層只往下依賴。例如渲染層不知道 YouTube 的存在，也不知道反覆記號。

## 6. 譜資料格式（v2，已用樣本驗證）

設計目標：**Claude 轉換 PDF 時好寫、人好讀好改、貼進 App 好展開。**

- 譜上小節照 PDF 的樣子記錄，小節號用譜上印的號碼。
- 常重複的節奏型存成 `patterns`，小節只引用名字。這樣 Claude 轉換時不用每小節重寫 6 行，也更不容易抄錯。
- 反覆與演奏順序放在 `form`，由 App 展開。

```json
{
  "version": 2,
  "title": "Dance Monkey",
  "youtubeId": null,
  "bpm": 95,
  "firstBeatSec": null,
  "timeSig": "4/4",
  "grid": 16,
  "lanes": ["CY", "HH", "T1", "SN", "FT", "BD"],
  "patterns": {
    "groove":  ["----------------", "----------------", "----------------", "----x-------x---", "----------------", "x-------x-------"],
    "chorus":  ["----------------", "x-x-x-x-x-x-x-x-", "----------------", "----x-------x---", "----------------", "x-------x-------"]
  },
  "bars": [
    {"n": 1,  "to": 8,  "rest": true, "section": "Intro"},
    {"n": 13, "to": 19, "use": "groove", "section": "Pre-Chorus"},
    {"n": 21, "to": 24, "use": "chorus", "section": "Chorus"}
  ],
  "form": [
    {"from": 1,  "to": 20},
    {"from": 21, "to": 24, "times": 2, "assumed": true}
  ],
  "anchors": [],
  "notes": "待確認事項寫在這裡"
}
```

欄位說明：

- `bars[].n` / `to`：譜上小節號範圍（含頭尾）。多小節休止就是一個 `rest: true` 的範圍。
- `bars[].use`：引用 `patterns` 的名字；也可以改成直接寫 `p`（6 行字串）。
- `form[]`：演奏順序，`times` 是總共演奏幾次；`assumed: true` 表示譜上沒標次數、是猜的，App 要在畫面上提醒。
- `section`：段落名稱，用在「從 Chorus 開始練」。
- 預留、v1 不實作：`anchors`、`grid: 12`（三連音）、拍號變化。

與原型的差別：原型是「一小節一組 6 行」的平面清單，沒有反覆與譜上小節號，要升級成這個格式。

## 7. 每首新歌的流程（目標：熟了之後 5 分鐘內）

1. 把老師的 PDF 傳給 Claude，用固定的指令轉成上面的 JSON；Claude 同時列出「看不確定的地方」（反覆次數沒標、特殊記號、不確定的音符）。
2. 在 App 按「匯入」，貼上 JSON。
3. 貼 YouTube 連結，App 取出影片 ID。
4. **兩點對拍**（只做一次）：播放時，在第一個進場的小節按一下標記，再在接近結尾的小節按一下，App 由這兩點算出 BPM 與第1拍位置；之後用 ±0.01 秒微調。譜上的 ♩= 只當初始值。
5. **驗證**：用 A-B 循環聽第一段、中間、最後一段，確認三處都對得上；特別檢查 `assumed` 的反覆。
6. 存進曲庫。

## 8. 部署與儲存（影響「以後好不好做」的關鍵）

**重要限制**：Claude 的 artifact 沙盒不允許載入 YouTube 的 iframe／腳本，所以 YouTube 版**不能**放在 artifact 裡，要自己託管。

建議：

- **託管**：靜態網頁放 GitHub Pages（免費），iPad Safari 開啟後「加入主畫面」，變成像 App 的全螢幕網頁。程式碼公開沒關係，因為裡面不放任何譜。
- **譜資料**：存在 iPad 本機（IndexedDB／localStorage），**不進公開 repo**。老師的譜有版權，只供個人使用。
- **備份**：提供「匯出全部曲目」按鈕，定期存到檔案或 iCloud。
- **維持單檔**：沿用你其他 App 的做法，一個 `index.html` 加少量輔助檔，不引入建置工具，之後 Claude 改起來最容易。

## 10. 風險與待查

1. **YouTube 時間精度**：播放時間只能用輪詢取得，需要本地插值平滑；iPad 上的實際誤差要靠 Spike 驗證，不能憑空假設。
2. **有些影片禁止內嵌**（唱片公司設定）：要先確認老師用的歌能不能嵌。備案：另開 YouTube，App 只跑譜與節拍器，手動同步開始。
3. **內嵌廣告或緩衝**會讓影片時間暫停，要偵測播放狀態並暫停譜面，恢復後重新對齊。
4. **反覆次數猜錯**：譜上有時沒標次數（樣本的第一段副歌就沒標），轉換時只能猜。用 `assumed` 標出來，驗證時對照影片，並在 v2 提供 App 內修改。
5. **PDF 轉換正確率**：樣本譜用的是標準鼓譜位置，目前看起來沒問題，但每換一個譜來源要重新確認圖例；Claude 要標出不確定處並由你抽查。
6. **簡化版譜 vs 原曲**：若老師省略了前奏或某些小節，需要靠對拍或錨點吸收差異。
7. **小孩使用體驗**：按鈕要夠大、操作要少；播放頁不放多餘設定。

## 12. 樣本譜分析：Dance Monkey（Drums Easy）

**基本資料**：4/4、♩=95，共 2 頁，譜上 60 小節。

**鼓的圖例（標準打擊樂譜表，與原型的 6 軌相容）**

- 底鼓：最下面的間
- 小鼓：第三間
- 踩鑔：× 符頭，畫在最上面
- 這份只用到這三種，沒有嗵鼓與銅鈸；也沒有十六分音符，只有四分和八分。

**樣本裡出現的記號，以及 App 該怎麼處理**

| 譜上的樣子 | 意義 | 處理 |
|---|---|---|
| 小節 1 上面的粗橫線＋「8」 | 連續休止 8 小節（1–8） | 展開成 8 個空小節；這正好是「何時進場」痛點的典型情境：第 9 小節才進場 |
| 小節 11 的「2」 | 休止 2 小節（11–12） | 同上 |
| `\|:` … `:\|` 加「4x」「3x」 | 這 4 小節反覆，共演奏 4 次／3 次 | 用 `form.times` 展開 |
| 第 21–24 小節只有反覆記號、沒標次數 | 次數不明，暫定 2 次 | `assumed: true`，待確認 |
| 段落標題（Intro、Pre-Chorus、Chorus…） | 歌的結構 | 存成 `section`，用於「從這段開始」 |
| 每小節上方的小節號 | 譜上小節號，**不計反覆** | 畫面顯示譜上小節號 |
| 第 31 小節全音符在底鼓位置 | 暫解讀為第1拍一下底鼓 | `note` 標記待確認 |

**數字**

- 譜上 60 小節，展開後演奏 **84 小節**（第一段副歌 ×2、第二段 ×4、第三段 ×3）。
- ♩=95 時總長約 **3:32**。YouTube 影片長度約 3:29–3:30，第一段副歌 ×2 最吻合，已確認。
- 若影片長度大致等於譜的長度，影片實際速度約 96 BPM，比譜上的 95 快約 1%。到歌尾會累積約 2–3 秒（接近一小節）的落差，所以對拍要用兩點校準，不能只靠譜上的 ♩=。
- 第一個有聲音的小節是第 9 小節，前面 8 小節完全休止。

**結論**

1. 多小節休止與反覆記號不是進階功能，第一首樣本就有，**必須放進 v1**（原先排在第 3 階段，已調整）。
2. 轉換格式要區分「譜上小節號」與「播放順序」，否則畫面上的小節號會和紙上的對不起來。
3. 這份譜的節奏型很少（4 種），用 `patterns` 引用可以大幅降低轉換出錯的機會。

轉換結果：`dance-monkey.json`（`youtubeId` 與 `firstBeatSec` 留空，等對拍時填）。
